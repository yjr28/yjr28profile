Kestrel is a distributed-systems flight recorder and failure-replay project. It reconstructs causal relationships from recorded events, compares healthy and failing requests, and tests whether a controlled fault can be reproduced.

Instead of stopping at a trace that shows what failed, Kestrel asks where the executions first diverged and whether the same failure schedule produces an equivalent outcome.

01 / Request topology

The current vertical slice models ten logical services. The local Go implementation uses separate TCP listeners within one process; the browser demo runs the core packages in WebAssembly with an adapter in place of the socket layer.

02 / From recorded events to evidence

Capture

Normalize service, operation, timestamps, trace and span identifiers, message IDs and fault metadata.

Reconstruct

Build a causal graph from parent/child spans, publish/consume pairs and supported fault-to-span evidence.

Compare

Compare healthy and faulty application evidence to identify an early meaningful divergence.

Edges represent recorded evidence, not proof of every possible causal relationship.

03 / What replay actually verifies

Kestrel implements Level-B failure-schedule replay for the tested latency fault. It applies the recorded seed, target, trigger position and delay to a fresh execution, then compares the outcome signature: failure classification, HTTP status, terminal service, error code and causal path. It does not promise identical execution timing or arbitrary deterministic distributed replay.

04 / Engineering boundary

Kestrel engine

Go fault injection, normalized event model, causal graph reconstruction, divergence detection and replay equivalence. The browser adapter executes the actual core packages and translates recorded spans for visualization.

Open-source visualization

The trace viewer reuses Jaeger UI v2.23.0 under Apache-2.0. Search, comparison and trace visualization are upstream features. The Kestrel replay workbench provides the project-specific experiment controls.

05 / Current scope

The repository documents a working first vertical slice, not a production-ready multi-process system. OpenTelemetry-native instrumentation, persistent storage, Rust/eBPF evidence, broader replay coverage and reproducible performance benchmarks remain planned. No throughput or overhead claims are made here.
